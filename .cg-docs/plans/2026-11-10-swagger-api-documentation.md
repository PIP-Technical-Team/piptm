# Plan: Overhaul Swagger/OpenAPI Documentation for All Plumber Endpoints

## Objective

Rewrite and enrich the OpenAPI/Swagger documentation generated by `inst/plumber/plumber.R` so that Swagger UI (`/__docs__/`) clearly documents the API overview, groups all 15 endpoints into intuitive workflow tags, provides complete single-line `@param` descriptions (fixing Plumber's multi-line truncation bug), marks required vs. optional parameters with concrete examples/enums/defaults, and exposes accurate top-level JSON `requestBody` schemas and examples for `POST /description` and `POST /table/download`.

## Context

Inspecting `pr$getApiSpec()` on `inst/plumber/plumber.R` reveals why the current Swagger UI is difficult to read and use:
1. **Multi-line `@param` truncation bug**: Plumber's comment parser only reads the first line of `#* @param` and concatenates wrapped continuation lines onto the endpoint's `description`. In `/table` and `/cell-definition`, parameter descriptions like `poverty_line`, `ppp`, `filter_base`, `pop_share_threshold`, and `include_metadata` are cut off mid-sentence (`"Poverty line value (required when"`, `"PPP reference year (optional; default 2021). Must be a"`), while their orphaned second lines form a garbled endpoint description.
2. **Wrapped summary lines**: `POST /description` and `GET /cell-definition` wrap their opening sentence across two lines, splitting the sentence between `summary` and `description`.
3. **Placeholder API header & ungrouped endpoints**: `spec$info` shows `"API Title"` / `"API Description"` and no `@tag` annotations exist, so all 16 operations sit in a single flat `default` group.
4. **Required parameters shown as optional (`required: false`)**: Because handler formals default to `= NULL` so custom 400 validation runs, OpenAPI marks every parameter `required: false` and emits 46 `Argument of class NULL cannot be used to set default value` warnings.
5. **Nested `{"body": {}}` schema on POST JSON endpoints**: `@param body:object` causes Plumber to generate a schema wrapped in `{"body": {...}}` with no examples, instead of documenting the actual top-level JSON body for `POST /description` and `POST /table/download`.

## Implementation Steps

### 1. Add API-level header & workflow tags in `inst/plumber/plumber.R`
- **Requirements**: R1
- **Files**: `inst/plumber/plumber.R`
- **Details**: Add `@apiTitle`, `@apiDescription` (covering the 3-step Table Maker workflow, standard JSON response envelope, error status codes, and `filter_base` / `pip_id` conventions), `@apiVersion`, and `@apiTag` definitions (`1. Step 1 — Survey Selection`, `2. Step 2 — Table Configuration`, `3. Step 3 — Table Computation & Export`, `4. System & Metadata`), and tag every endpoint with `@tag`.
- **Tests**: `tests/testthat/test-api-endpoints.R`
- **Acceptance criteria**: `spec$info` and `spec$tags` are populated and every operation has an assigned workflow tag.

### 2. Rewrite endpoint & parameter roxygen blocks in `inst/plumber/plumber.R`
- **Requirements**: R2
- **Files**: `inst/plumber/plumber.R`
- **Details**: Give every endpoint a single-line `#*` summary and a structured Markdown `#*` description (Purpose, When to use, Parameter usage notes, Example request). Make every `#* @param` annotation a single unbroken line that clearly states what the parameter represents, whether it is required/conditional/optional, its format/allowed values, default, and an example.
- **Tests**: `tests/testthat/test-api-endpoints.R`
- **Acceptance criteria**: No `@param` description is truncated in `pr$getApiSpec()` and no orphaned parameter continuation lines leak into operation `description` fields.

### 3. Add `pr$setApiSpec()` OpenAPI post-processor in `inst/plumber/plumber.R`
- **Requirements**: R3
- **Files**: `inst/plumber/plumber.R`
- **Details**: In the `#* @plumber` hook, configure `pr$setApiSpec()` to: (a) mark required query parameters (`analysis_var`, `pip_id`, `measures` on `/table`; `analysis_var`, `measures` on `/cell-definition`; `country_code`, `year`, `welfare_type` on `/lookup`), (b) attach concrete `example` / `enum` / `default` metadata to parameters across all endpoints, (c) replace the wrapper `{"body": {}}` schema on `POST /description` (Fast Path and Fallback Path examples) and `POST /table/download` (CSV/RDS Approach C payload example) with accurate top-level `requestBody` schemas and interactive examples, and (d) document standard response codes (`200`, `400`, `413`, `422`, `500`).
- **Tests**: `tests/testthat/test-api-endpoints.R`
- **Acceptance criteria**: `pr$getApiSpec()` contains accurate required flags, parameter examples/enums, top-level `requestBody` schemas with named examples, and response descriptions, without changing any runtime endpoint behavior.

### 4. Add OpenAPI spec contract tests and verify full suite
- **Requirements**: R4
- **Files**: `tests/testthat/test-api-endpoints.R`
- **Details**: Add a test block in `tests/testthat/test-api-endpoints.R` that inspects `pr$getApiSpec()` across all 15 endpoints (16 operations) to assert non-empty summaries, descriptions, workflow tags, complete parameter descriptions, required flags, parameter examples, and `POST /description` + `POST /table/download` `requestBody` schemas.
- **Tests**: `tests/testthat/test-api-endpoints.R`
- **Acceptance criteria**: All OpenAPI spec assertions and all existing API runtime tests pass.
