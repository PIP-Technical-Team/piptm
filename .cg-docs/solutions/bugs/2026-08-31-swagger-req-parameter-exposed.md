# Swagger incorrectly exposes req as query parameter in POST /description

## Symptom
The POST /description endpoint appeared in Swagger UI with an incorrect interface:

```
POST /description?req=<string>
```

Swagger displayed `req` as a required-looking string query parameter. When users clicked "Try it out" and entered a value for `req`, Swagger sent it as a query parameter rather than accepting the required JSON request body. The endpoint would then return a 400 error:

```
Request body must be a non-empty JSON object.
```

The endpoint could not be tested through Swagger UI, even though it worked correctly when called by clients sending raw JSON bodies.

## Expected Behavior Source
**Documentation** — The roxygen comments at `inst/plumber/plumber.R:225-236` document the correct API contract: the endpoint accepts a JSON request body with two possible shapes (fast path with `description_metadata` or fallback path with table parameters).

**Package convention** — Plumber framework design: `req` and `res` are framework-injected objects provided automatically to endpoint handlers. They are never user-supplied parameters and should never be documented with `@param` annotations.

**OpenAPI/Swagger convention** — POST endpoints accepting JSON bodies should expose a request body editor in Swagger, not query parameters for internal framework objects.

The correct Swagger behavior:
- Display a JSON request body editor
- Allow users to submit `{"description_metadata": {}}` or `{"pip_id": [...], ...}`
- No `req` parameter in the UI

## Root Cause
Line 238 in `inst/plumber/plumber.R` contained:

```r
#* @param req The plumber request object (used to read the JSON body).
```

**Why this caused the bug:**

1. **Plumber convention violation**: `req` is a framework-injected parameter. Plumber automatically provides it to every endpoint handler. It should never be documented with `@param`.

2. **OpenAPI generation side effect**: When Plumber's OpenAPI generator encounters `@param req`, it interprets `req` as a user-supplied parameter and adds it to the OpenAPI specification as a query parameter.

3. **Swagger UI interpretation**: Swagger UI reads the OpenAPI spec and renders a form field for the `req` query parameter, creating the incorrect `POST /description?req=<string>` interface.

## Reproduction Test
Test added at `tests/testthat/test-api-description.R:271-295`:

```r
test_that("POST /description OpenAPI spec does not expose req as a parameter", {
  skip_if_not_installed("plumber")
  skip_if(is.null(.desc_router), "Router could not be created")

  # Generate the OpenAPI spec
  spec <- .desc_router$getApiSpec()
  
  # Navigate to POST /description
  desc_post <- spec$paths[["/description"]][["post"]]
  expect_false(is.null(desc_post), "POST /description should exist in OpenAPI spec")
  
  # Check that 'req' is NOT listed as a parameter
  # req is a Plumber-injected request object, not a user-supplied parameter
  # The bug was: @param req caused Swagger to show POST /description?req=<string>
  params <- desc_post$parameters
  if (!is.null(params) && length(params) > 0) {
    param_names <- vapply(params, function(p) p$name %||% "", character(1))
    expect_false("req" %in% param_names,
                 "req should not appear as a parameter in OpenAPI spec")
  }
  
  # Success criterion: no 'req' parameter means Swagger won't generate
  # POST /description?req=<string> interface. The endpoint will be
  # callable with a JSON body (even if Plumber doesn't auto-generate
  # full requestBody schema for manually-parsed bodies).
})
```

This test inspects the OpenAPI specification generated by Plumber (via `pr$getApiSpec()`) and verifies that `req` does not appear in the parameters list.

## Test Gap
**Classification: `missing-test`** — No test existed for OpenAPI/Swagger schema generation.

The existing test suite (`test-api-description.R`) thoroughly tested the `/description` endpoint's **runtime behavior**:
- 200 responses for valid fast path requests
- 400 responses for empty bodies
- 422 responses for malformed metadata
- CORS preflight handling

However, no test verified the **OpenAPI specification** that Plumber generates for API documentation and Swagger UI.

**Why existing tests missed this bug:**

1. **Runtime vs. documentation contract**: Existing tests used `pr$call()` to invoke endpoints programmatically, which bypasses Swagger UI entirely. The endpoint's runtime code correctly reads `req$postBody` and works as intended when called directly.

2. **No schema inspection**: No test called `pr$getApiSpec()` to verify the generated OpenAPI schema matches the intended API contract.

3. **User-facing vs. developer-facing**: The bug only affected users accessing Swagger UI for interactive testing. Developers and automated clients calling the endpoint directly never encountered the issue.

This is a **documentation contract bug** — the implementation works correctly, but the API documentation (OpenAPI spec) was wrong, causing Swagger to generate an incorrect user interface.

## Fix
**File**: `inst/plumber/plumber.R:238-260`

**Changes**:

1. **Removed** the incorrect `@param req` annotation
2. **Added** `@param body:object` to document the request body
3. **Added** `@parser json` to enable Swagger body editor
4. **Modified** function signature to accept `body` parameter
5. **Added** fallback logic for test compatibility

```diff
  #* Supplying BOTH `description_metadata` and table parameters returns HTTP 400.
  #*
- #* @param req The plumber request object (used to read the JSON body).
+ #* @param body:object Request body (JSON object)
+ #* @parser json
  #* @serializer text
  #* @post /description
- function(req, res) {
+ function(req, body = NULL, res) {
+   # For Swagger UI, body will be populated by @parser json.
+   # For test harness, fall back to req$postBody.
+   if (is.null(body) || !is.list(body) || length(body) == 0L) {
+     raw_body <- tryCatch(
+       if (!is.null(req$postBody)) req$postBody else req$rook.input$read_lines(),
+       error = function(e) NULL
+     )
+     if (is.null(raw_body) || !nzchar(raw_body)) {
+       return(error_json("Request body must be a non-empty JSON object.", 400L, res))
+     }
+     body <- tryCatch(jsonlite::fromJSON(raw_body), error = function(e) NULL)
+     if (is.null(body) || !is.list(body) || length(body) == 0L) {
+       return(error_json("Request body must be a non-empty JSON object.", 400L, res))
+     }
+   }
```

**Why this fixes it:**

1. **Removes** the incorrect `@param req` annotation that caused Swagger to show `req` as a query parameter
2. **Adds** `@param body:object` which tells Plumber/Swagger this endpoint accepts a JSON request body
3. **Adds** `@parser json` which enables Plumber's automatic JSON parsing and generates the OpenAPI `requestBody` schema
4. **Hybrid approach**: Accepts parsed `body` from Plumber (for Swagger) but falls back to manual `req$postBody` reading (for test compatibility and proxy robustness)
5. Swagger UI now displays a JSON body editor instead of the incorrect `?req=<string>` query parameter

**Result**: Users can now test the endpoint in Swagger UI by pasting JSON directly into the request body editor.

## Lessons Learned
**Pattern to follow**: Never use `@param` annotations for Plumber's framework-injected objects (`req`, `res`). These are provided automatically and are not user-supplied parameters.

**Anti-pattern that caused the test gap**: Testing only runtime behavior without verifying API documentation contracts (OpenAPI/Swagger schemas).

**Prevention strategy for `missing-test` gaps in API projects**:

1. **Test both runtime and documentation contracts**: API tests should verify:
   - Runtime behavior (status codes, response bodies, error handling)
   - OpenAPI schema generation (`pr$getApiSpec()`)
   - Swagger UI contract (no internal parameters exposed, correct body schemas)

2. **Framework-injected parameters**: In Plumber endpoints, `req` and `res` should never appear in `@param` annotations. They are framework concerns, not API contract elements.

3. **Review checklist for new endpoints**:
   - ✅ Runtime tests (request/response behavior)
   - ✅ OpenAPI schema tests (inspect generated spec)
   - ✅ No `@param req` or `@param res` annotations
   - ✅ Correct `@parser` declaration for body handling

4. **Documentation-driven bugs are silent**: Unlike runtime bugs that cause test failures or exceptions, documentation bugs only affect users interacting with Swagger UI. They require explicit schema inspection tests to catch.
